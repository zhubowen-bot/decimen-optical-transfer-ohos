# Decimen Optical Transfer — HarmonyOS 移植计划

## Goal

在 `ohos/` 子目录中新建一个完整的 HarmonyOS NEXT ArkTS 应用，实现与原 Web 版 **decimen-optical-transfer**（decimen.app）**字节级互通**的"屏幕→摄像头"文件/文本传输：

- **发送端**：选择文件或输入文本片段 → gzip（仅当有益）+ SHA-256 + 自描述容器打包 → 系统轮播喷泉编码（LTEncoder）→ **字节精确 QR 编码**（移植 `qrcode` 生成器）→ Canvas 上以可配置速率/ECC/网格数动态渲染（网格错相翻页）。
- **接收端**：摄像头取帧（Camera Kit + ImageReceiver）→ 灰阶化 → **区域裁剪追踪 + TaskPool 并行 jsqr 解码**（移植 `jsqr`）→ `parseFrame` → LTDecoder 喷泉解码 → FNV-1a + 容器内 SHA-256 双重校验 → 文本展示/复制或文件保存（DocumentViewPicker）。
- 与 Web 版完全互通：鸿蒙发送的流可被 decimen.app 网页接收，网页发送的流可被鸿蒙手机接收（同一帧头 magic、同一 dlog 确定性对数、同一容器格式）。

## Scope / Non-goals

**In scope（v1 核心功能完整）**
- 文件（≤64 MB）与文本片段（≤4 MB）发送/接收
- 容器打包：文件名/媒体类型保留、条件 gzip、SHA-256 与 FNV-1a 校验
- 发送参数：fps（10/15/20/24/30/55/60）、bytes-per-frame（500/1000/1465/1850/2331/2953）、ECC（L/M/Q/H）、网格码数（1/2/4/6）、显示尺寸；规格展示（QR 版本、K、压缩率）
- 接收端：实时预览+解码框叠加、进度/速率/ETA、区域追踪、全帧重扫描、"无信号"提示、文本复制、文件保存与图片/视频/音频预览
- 屏幕常亮（传输期间）；首页（发送/接收入口）

**Non-goals（v1 明确不做）**
- 多码网格接收端的像素级**裁剪追踪**完整复刻可降级为"全帧扫描+区域缓存"（见设计）；Web 的 `?capture=bitmap` 路径不做
- 诊断/基准模式（`npm run diagnostics` / `benchmark`）不移植
- PWA/离线安装/分享对话框（OS 原生分享按钮可用 `@ohos.ability.particle` 后续加，v1 不做）
- 多码网格发送的**逐格 ImageData 局部重绘**优化——v1 用整网格 writePixels + drawImage（功能等价，性能后续优化）
- 纯 OpenHarmony（非华为商业版）设备兼容性：依赖 Camera Kit/ImageReceiver，为 OpenHarmony NEXT 公共 API，但仅验证 HarmonyOS NEXT 真机

## Current State And Constraints

**源项目（web）结构**
- `shared/`：`protocol.ts`（20B 帧头、容器、FNV-1a、splitmix32）、`fountain.ts`（v2 系统轮播 LT 码 + 确定性 dlog）、`frame-capacity.ts`、`qr-raster.ts`、`progress.ts`、`send-settings.ts`、`snippet.ts`、`format.ts`、`no-signal.ts` 等 —— 全部纯逻辑，**无 DOM**，可直接逐行移植
- `send/main.ts`：qrcode npm 库生成 QR + Canvas 栅格 + 网格错相翻页
- `receive/main.ts` + `worker.ts`：zxing-cpp WASM 解码 + 区域追踪 + 全帧扫描
- `tests/`：**黄金向量测试**（fountain.test.ts 的 dlog 逐位向量、protocol/snippet/qr-raster 等）—— 移植后用于验证字节精确性

**关键约束**
1. **跨引擎确定性**：Web 版 dlog() 存在的理由就是 JS 引擎（V8/JSC）的 `Math.log` 可能差 1 ulp，足以翻转采样的 degree 使双方静默失步。ArkVM 是第三个引擎，因此移植 `fountain.ts` 时必须**逐行照搬 dlog 的显式 IEEE-754 运算序列**（不得替换为 `Math.log`），且 `splitmix32`、`Math.imul`、`>>>`、`Math.floor`、`Math.sqrt` 等确定性运算全部原样保留。用 `tests/fountain.test.ts` 的黄金值（含全区间 FNV 摘要 `0x27b0f3cc`）验证。
2. **字节精确 QR 编解码**：鸿蒙无公开的字节级 QR 生成 API（`QRCode` 组件仅接受字符串，ScanKit 是闭源且返回字符串，对二进制帧有损坏风险——用户已确认放弃）。必须移植 `qrcode`（MIT）与 `jsqr`（MIT）到 ArkTS；两者均纯 TS/纯算术。
3. **ArkTS 严格模式**：移植时禁用 `any`/`unknown`/`as` 断言滥用/结构化类型/索引签名/解构/`Object.assign`；对象字面量需具名 interface；`T | undefined` 窄化；`@kit.*` 命名空间正确（`camera`=`@kit.CameraKit`，`image`=`@kit.ImageKit`，`fileIo as fs`/`picker`=`@kit.CoreFileKit`，`cryptoFramework`=`@kit.CryptoArchitectureKit`，`zlib`=`@kit.BasicServicesKit`，`hilog`=`@kit.PerformanceAnalysisKit`）。每次写 .ets 前对照 arkts-grammar-standards 技能（Top-5 陷阱表）。
4. **许可**：qrcode/jsjr 为 MIT，移植后在 `ohos/` 下 NOTICE 中保留归属；整体沿用仓库 AGPL-3.0-or-later。
5. 工程在 `ohos/` 子目录，**不修改任何现有 Web 文件**。

### 模块移植映射

| Web 文件 | ArkTS 文件 | 移植要点 |

| `shared/fountain.ts` | `common/Fountain.ets` | **逐行移植 dlog/solitonCdf/frameComposition/repairIndices**；LTEncoder/LTDecoder 用 `Map<number, Set<PendingFrame>>`、`(Uint32Array \| undefined)[]`；不加任何优化以免破坏 wire 格式 |
| `shared/frame-capacity.ts` | `common/FrameCapacity.ets` | 原样 |
| `shared/snippet.ts` | `common/Snippet.ets` | 原样（media type `application/vnd.decimen.snippet` 不变） |
| `shared/format.ts` `send-settings.ts` `no-signal.ts` `progress.ts` | 同名 | 原样；fps/bytes 列表、提示文案常量保持一致 |
| `shared/qr-raster.ts` | `common/QrRaster.ets` | 栅格化保留（u32 小端白/黑像素）；注意黑=字节 `00 00 00 FF`、白=`FF FF FF FF`，R=G=B 无需纠结 BGRA/RGBA |
| `node_modules/qrcode/lib/core/*` | `qr/QrEncoder.ets` | 移植 galois-field/polynomial/bit-buffer/bit-matrix/mask-pattern/error-correction-code/error-correction-level/mode/qr-version/format-info/alignment-pattern/utils/qr-code；Buffer→Uint8Array；仅 byte mode；支持 version 1–40、ECC L/M/Q/H、`maskPattern` 固定 4；入口 `create(segments, {version, errorCorrectionLevel, maskPattern})` 返回 `{modules: BitMatrix, version}` |
| `node_modules/jsqr/dist/*` | `qr/QrDecoder.ets` | 移植 binarizer/locator/extractor/decoder/bitmat/version/finder；入口 `decode(data: Uint8ClampedArray, width, height)` → `{data: Uint8Array, location, chunks} \| undefined`（RGBA 输入） |

### 发送端设计

1. **选择/输入**：文件用 `picker.DocumentViewPicker().select()`（`DocumentSelectOptions`），`fs.statSync(uri).size` 先校验 ≤64MB/非空，`fs.openSync+readSync` 读字节；片段用 `TextArea`。
2. **打包**（`SendEngine.ets`）：`packFile/packSnippet` → 条件 gzip（`GzipWrap`，用 `@ohos.zlib` `Zip.compressBuffer`，压缩后尺寸+64 < 原尺寸才用，与 Web 判定一致）→ SHA-256（`CryptoWrap`，`cryptoFramework.Md`）→ 容器。
3. **流生成**：`LTEncoder(payload, blockLen, sessionId)` + `fnv1a(payload)`；每帧 `packFrame` → `QrEncoder.create`（首个帧锁定 version，后续复用）→ `QrRaster` 栅格 → 按 `gridDims` 拼成整网格 RGBA 缓冲（复用 Web 的 `rasterizeQrGrid` 逻辑）。
4. **渲染循环**：`Canvas(this.context)`，`onReady` 后启动 `setInterval`（间隔 `1000/txFps`，网格错相 `subInterval = interval/gridCodes`），每 tick：更新网格缓冲 → 构造一张 `image.PixelMap`（`image.createPixelMap`，RGBA_8888，grid 尺寸，流开始时创建一次）→ `pixelMap.writePixels(网格RGBA)` → `ctx.drawImage(pixelMap, 0,0,w,h)`。队列/lookahead/pump 模式照搬 send/main.ts 防卡顿。`aboutToDisappear` 清理定时器。
5. **参数面板**：fps/bytes/ECC/网格数/显示尺寸选择器 + 规格展示（V/ECC/K/压缩）+ 状态行 + 无信号提示文案；`window.getLastWindow().setWindowKeepScreenOn(true)` 保持常亮（API 名以 SDK 为准，若不存在则用 `@ohos.runningLock`）。

### 接收端设计

1. **摄像头**（`CameraCapture.ets`）：申请 `ohos.permission.CAMERA`；`camera.getCameraManager(context)` → 后置摄像头 → `getSupportedOutputCapability` → 选与目标分辨率最接近的 `videoProfile` → `image.createImageReceiver(w, h, YUVC420_SP, 4)` → `camera.createVideoOutput(profile, receiver.getReceivingSurface())` → `videoOutput.start()`。`receiver.on('imageArrival')` → `readLatestImage()` → `getComponent(ComponentType.YUV_YUYV)` → 取 Y 平面做灰阶（R=G=B=Y）→ `image.release()`。
2. **解码流水线**（`DecodePipeline.ets`）：主线程做区域追踪（Region：box+decoded+drift），逻辑移植自 receive/main.ts 的 `noteRegion/layoutOrder/scanInterval`（TTL 1500ms、健康全扫 800ms、退化 250ms、获取 100ms）。每次取帧：到期区域裁剪 → 灰阶缓冲 → `taskpool.execute(decodeTask, grayBuffer, w, h, ox, oy)` 分发（用 `taskpool.Task` + transfer 列表传 ArrayBuffer）。`@Concurrent` 函数内跑 jsqr `decode` → 返回 `{bytes?, box?}`。解码在主线程 `parseFrame` + 喂 `LTDecoder`（解码本身便宜，主线程即可）。
3. **进度**：移植 `estimateTransferProgress`，按 `framesNew - framesRedundant` 计有效帧；显示捕获/解码 fps、KB/s、ETA、K、块数。
4. **收尾**（`ReceiveEngine.ets`）：`decoder.isComplete` → `assemble` → `fnv1a(payload)===header.payloadFnv` → `unpackFile` → `verifyFile`（SHA-256）→ 片段显示+`pasteboard` 复制；文件用 `picker.DocumentViewPicker().save({newFileNames:[name]})` 保存，图片/视频/音频用 `Image`/AVPlayer 预览（视频走临时 `filesDir` 文件）。

### ArkTS 关键决策（生命周期/状态/并发）

- **状态**：SendPage/ReceivePage 用 V1 `@State`/`@Prop`；Canvas 渲染用命令式绘制，不走状态驱动重绘（见 kit-api-quick-ref §9 游戏循环模式）。
- **生命周期**：相机开启/关闭在 `aboutToAppear/aboutToDisappear` + `onPageHide/onPageShow`（传输中途切后台要停帧采样并提示）；发送循环在 `aboutToDisappear` 清理 `setInterval`。
- **并发**：jsqr 解码用 `@ohos.taskpool`（`@Concurrent` 顶层函数 + `@Sendable` 结果类）；LTDecoder/协议解码留在主线程。
- **导航**：`Navigation` + `NavDestination`（Index→Send/Receive），或直接三个 `main_pages.json` 页面 + `router`——选用 **Navigation** 组件树（推荐）以符合鸿蒙 5 规范。
- **资源**：新增 string 资源（标题、提示文案）到 `resources/`；不依赖 `sys.media.*`（用文本/emoji）。

## Execution Sequence

1. **脚手架**：按 `deveco-create-project` 技能在 `ohos/` 创建工程（Stage 模型，compileSdkVersion ≥ API 12，语言 ArkTS）；配置 `module.json5`（CAMERA 权限 + 页面注册）、应用图标/名称、NOTICE。
2. **纯逻辑移植（无 UI 依赖）**：按映射表移植 Protocol/Fountain/FrameCapacity/Snippet/Format/SendSettings/Progress/NoSignal/QrRaster 到 `.ets`。**每个文件写完立即 `arkts_check`**。
3. **系统包装**：`GzipWrap`（`@ohos.zlib` createZipSync().compressBuffer/decompressBuffer，gzip 格式）与 `CryptoWrap`（`@ohos.security.cryptoFramework` MD5/SHA-256 digest）——注意 zlib API 需预分配目标缓冲、返回 status；decompress 前先解析 gzip 尾部 ISIZE 做上限防护（对齐 Web 的 `gunzipAsync` 防膨胀逻辑）。
4. **黄金向量测试**：把 `tests/fountain.test.ts`（dlog 11 个逐位值 + 全区间 FNV 摘要 `0x27b0f3cc`、frameComposition 向量）、`tests/protocol.test.ts`、`tests/snippet.test.ts`、`tests/qr-raster.test.ts` 翻译为 hypium 用例，跑通后再进入 UI。
5. **QrEncoder 移植**：移植 qrcode core；用 Web 端 `node -e`（tsx 加载原库）对 500/1465/2953 字节载荷生成黄金矩阵与版本，写为 hypium 用例逐模块比对。
6. **发送页**：SendEngine + Canvas 渲染循环 + 文件/片段输入 + 参数面板 + 规格/状态行；真机两屏对拍自测。
7. **QrDecoder 移植**：移植 jsqr；用第 5 步生成的 QR 矩阵栅格化 → 转为 RGBA → `decode` 还原字节，与原始帧字节比对（hypium 用例）。
8. **接收页**：CameraCapture → DecodePipeline（TaskPool）→ ReceiveEngine → 保存/预览/复制 → 无信号提示。先在模拟器用静态 QR 图验证 jsqr 链路，再真机验证动态流。
9. **互通验证 + 打磨**：鸿蒙↔Web 双向互收；性能采样；内存/崩溃检查；屏幕常亮；页面转场。

## Risks And Compatibility

- **跨引擎确定性（最高风险）**：ArkVM 双精度运算必须与 IEEE-754 逐位一致。黄金向量测试是唯一防线；dlog 严禁换成 `Math.log`。若 ArkVM 有异常（极不可能），唯一出路是帧头 magic 升版——需用户知晓为破坏性变更。
- **jsqr 在 ArkTS 的性能**：纯 TS 解码较 WASM 慢。缓解：灰阶输入、区域裁剪优先、TaskPool 并行、按需采样帧。v1 吞吐预期显著低于 Web（418KB/s 是 4 码 60fps WASM 的结果）；明确接受。
- **`qrcode` 移植保真度**：版本表（1–40）/GF 多项式/掩码表移植错一处则整帧失效——用 golden 矩阵测试覆盖。
- **Camera/ImageReceiver 设备差异**：YUV 格式、视频 profile 分辨率协商因机型而异；需按 capability 就近选择并做降级（如 640×480→1280×720）。
- **zlib API 语义**：`compressBuffer`/`decompressBuffer` 需要预分配缓冲与 status 检查；gzip 尾部 ISIZE 校验逻辑需与 Web 一致，防膨胀上限（clamp 到 MAX_FILE_BYTES）保留。
- **内存**：64MB 文件 + 容器 + 队列多份拷贝对手机有压力；发送端避免多余拷贝，接收完成即释放。
- **SDK 版本**：以 API 12 为基线（ImageReceiver/YUV、taskpool transfer、zlib API 12 接口均需 API 12+）；更高 API 的可选接口需运行时可探测。
- 华为闭源 kit（ScanKit）不采用，无该依赖。

- 不影响现有 Web 构建（`npm run build` / `npm test` 输入路径不变）。
- 若互通验证失败且根因在协议层（dlog/帧头），在 `common/Protocol.ets`/`Fountain.ets` 中回退到上一个 git 提交的版本即可；不影响 Web 侧。
